# Furuta rev18b 강화학습 알고리즘 비교 (교육용 키트)

목표는 두 가지뿐입니다.

1. **학습 시간 3분 미만** (짧을수록 좋음)
2. **학습 안정성** (시드를 바꿔도 같은 결과가 나오는가, 중간에 붕괴하지 않는가)

과제는 **스윙업 + 밸런싱**: 아래로 매달린 상태에서 시작해 진자를 세우고 유지합니다.
기준 하드웨어는 Ryzen 5 7500F (6코어) + RTX 4070 SUPER, Windows 11, Python 3.14.

```
pip install mujoco gymnasium stable-baselines3 sb3-contrib torch matplotlib
python rl/run_all.py --budget 180 --seeds 0 1 2 3     # 전체 벤치마크
python rl/plot_results.py                             # 그래프 + 표
python rl/bench.py --algo sac --seed 0 --budget 180 --save rl/sac_model
python rl/inspect_policy.py --algo sac --path rl/sac_model --alpha0 0
```

## 환경 설계

### MJCF 모델에서 바뀐 것 (XML 파일은 건드리지 않고 런타임에 설정)

| 항목 | 값 | 근거 |
|---|---|---|
| `armature` (arm 관절) | **5.0e-3 kg·m²** | README 미해결 항목 1. RMD-X6-P20의 감속비 20²을 반영한 추정치(로터 관성 약 1.25e-5 × 400). Arm 자체 관성 5.6e-5의 약 90배로, README가 경고한 "반사관성이 지배적인" 영역에 해당. **실측(토크 스텝 → 각가속도)으로 교체해야 하는 가정값입니다.** |
| 모터 속도-토크 곡선 | 무부하 속도 **16 rad/s** (≈153 rpm, 출력축) | MJCF의 `motor`는 속도와 무관하게 토크를 내므로, 암이 실제 모터로는 불가능한 속도까지 가속됩니다. 1차 곡선 `τ ≤ τ_stall(1 − |ω|/ω₀)`(구동 시, 제동은 전토크)을 넣어 물리적 속도 상한을 줬습니다. |
| 시뮬 타임스텝 | 1 ms → **2 ms** (RK4 유지) | 처리량 2배. 정확도 확인: 마찰 없이 170°에서 5초 자유운동 에너지 변동 **1.4e-6 J** (1 ms는 1.8e-7 J, 총 에너지 0.075 J 대비 0.002%), 미소진동 주기 **0.61422 s** (1 ms 0.61411 s, 실측 0.6141 s). |
| 제어 주기 | **50 Hz** (20 ms) | 200 Hz는 에피소드당 결정이 1000번이라 RL 샘플 효율이 나쁩니다. 50 Hz에서도 단순 선형 제어기로 도립 유지가 100% 되는 것을 확인(25 Hz에서도 99.3%). 진자 고유진동 1.63 Hz의 30배이고, CAN + I2C 기반 실기에 현실적입니다. |

> 속도-토크 곡선을 넣은 이유는 성능이 아니라 **꼼수 차단**이기도 합니다. 넣기 전에는 학습된
> 정책이 암을 27 rad/s로 계속 회전시켜 **원심력으로 진자를 수평에 띄워놓고** 보상을 받았습니다.
> 원심력이 중력을 이기는 임계는 θ̇ ≈ 19 rad/s라서, 16 rad/s 상한으로 이 해법이 사라집니다.

### 관측 / 행동

- 관측(6): `cos θ, sin θ, cos α, sin α, θ̇/20, α̇/40` — 각도 래핑 불연속을 없애기 위해 cos/sin 사용.
  Furuta 동역학은 θ에 무관하므로 `cos θ, sin θ`는 엄밀히는 불필요하지만, 암을 중앙으로 되돌리는
  항을 나중에 보상에 추가할 수 있도록 남겨뒀습니다.
- 행동(1): 정규화 토크 `u ∈ [-1, 1]` → `u × 1 N·m`. ±1 N·m는 모터 사양이 아니라 학습 안전 클램프입니다.
- 에피소드 5초(250스텝), 조기 종료 없음.

### 보상

φ = α − π 를 (−π, π]로 래핑한 값(0 = 도립):

```
r = 1 − 0.3 φ²  − 0.002 α̇²  − 0.002 θ̇²  − 0.02 u²
      + 0.5 · exp(−(φ/0.3)²) · exp(−(α̇/2)²)
```

모든 항이 유계이고 조기 종료가 없어서, 스텝당 보상이 **단조 증가하는 사다리**가 됩니다.

| 행동 | 스텝당 보상 |
|---|---|
| 매달린 채 가만히 | ≈ 0.01 |
| 빠르게 회전 | ≈ 0.3 |
| 분리선 근처 느린 회전 | ≈ 0.7 |
| 도립 유지 | **1.5** |

각 단계의 개선이 모두 보상되므로 중간에 갇히지 않습니다. 설계 과정에서 실패한 변형들:

- 보상이 평평하면(최대 1.3, ±75°에서도 0.8) 안정화할 이유가 없어 위쪽에서 크게 흔들기만 합니다.
- 벌점이 크고 조기 종료가 있으면 "일부러 빨리 끝내기"나 "가만히 있기"가 최적이 됩니다.
- 속도 벌점에 상한이 없으면 학습이 붕괴합니다(리턴 402 → −1075 관측).

### 탐색 시작(exploring starts)

학습 에피소드의 **절반**은 `α, θ ~ U(−π, π)`, `θ̇ ~ U(−2, 2)`, `α̇ ~ U(−6, 6)`에서 시작합니다.
도립 근처 상태를 초기부터 보게 해서 "잡는 기술"을 먼저 배우게 하는 표준 기법이고, 실기에서는
외란 복원력으로도 이어집니다. **평가는 항상 매달린 상태에서만** 시작합니다.

## 측정 방법

- x축은 **학습 벽시계 시간**이고, **평가에 쓴 시간은 시계에서 뺍니다**. 그래서 곡선의 180초는
  진짜 학습 180초입니다.
- 평가는 고정된 초기조건 5개(매달림 ± 작은 교란)에서 결정론적 정책으로 5초 롤아웃.
- **성공** = 5초 에피소드의 마지막 2초를 도립 ±10°, |α̇| < 2 rad/s 로 유지. 성공률은 5개 중 비율.
- 공정성을 위해 전 알고리즘 공통: 신경망 `[64, 64]`, γ = 0.99, PyTorch 스레드 1개,
  한 번에 한 프로세스만 실행(형제 작업으로 타이밍이 오염되지 않게).
- 알고리즘별 디바이스/병렬 환경 수는 **이 PC에서 가장 빠른 설정**을 측정해서 정했습니다
  (아래 "처리량" 참고). 알고리즘마다 병목이 다른데 한 설정을 강제하면 공정하지 않습니다.

### 알고리즘별 확정 설정

모두 추측이 아니라 이 PC에서 직접 재서 정했습니다 (조용한 기계 기준, 아래 "측정 환경 위생" 참고).

| 알고리즘 | 병렬 환경 | VecEnv | 디바이스 | 업데이트 비율(UTD) | 셋업 시간 |
|---|---|---|---|---|---|
| PPO, A2C | 24 | Subproc | CPU 1스레드 | — | 18.5 s |
| SAC, TD3, DDPG, TQC, CrossQ | 8 | Dummy | CPU 1스레드 | 0.125 (`gradient_steps=1`) | 4.0 s |

공통: 신경망 `[64, 64]` (CrossQ의 critic만 `[256, 256]`, 논문 권장), γ = 0.99, 버퍼 40만,
배치 256, `learning_starts` 2000.

**PyTorch 스레드 수** (PPO, Subproc 24, 30초):

| 스레드 | fps | 프로세스 CPU 점유 |
|---|---|---|
| **1** | **11,087** | 0.92 코어 |
| 2 | 10,272 | 1.67 코어 |
| 6 | 9,053 | 5.13 코어 |

6스레드는 **CPU를 5.6배 더 쓰면서 처리량은 18% 낮습니다.** 64×64 같은 작은 텐서에서는
스레드 동기화 비용이 계산보다 크기 때문입니다. 1스레드가 정답.

**병렬 환경 수와 VecEnv** (PPO, 1스레드, 30초):

| 구성 | fps | 셋업 |
|---|---|---|
| Dummy 32 | 6,549 | 4.7 s |
| Subproc 8 | 8,159 | 8.3 s |
| Subproc 12 | 9,582 | 11.1 s |
| **Subproc 24** | **11,743** | 18.5 s |
| Subproc 32 | 11,137 | 21 s |

24에서 평탄해지고 32는 셋업만 늘어납니다. 48은 비실용적입니다 — 윈도우는 `fork`가 없어
워커마다 torch·SB3·mujoco를 다시 임포트하는데, 프로세스 48개가 6코어에서 동시에 그걸 하면
스폰만 수 분이 걸립니다.

**디바이스.** 모든 알고리즘에서 CPU가 GPU보다 빠릅니다. SAC는 **17배** 차이입니다.

| 알고리즘 | GPU fps | CPU fps |
|---|---|---|
| SAC | 100 | **1,717** |
| TD3 | 278 | **1,385** |
| TQC | 229 | **517** |
| CrossQ | 198 | **403** |
| PPO | 2,293 | **3,422** (Dummy 32 기준) |

RTX 4070 SUPER가 있는 기계인데도 **쓰지 않는 쪽이 빠릅니다.** 커널 실행 오버헤드가
이 크기 신경망의 계산량보다 크기 때문입니다. 교육용 키트에 "GPU 필요"를 적을 이유가 없습니다.

**UTD 탐색** (SAC, 8환경 Dummy, 30초). off-policy는 그래디언트 계산이 병목이라 업데이트
비율이 벽시계 성능을 좌우합니다. 낮출수록 환경 스텝을 더 많이 모을 수 있습니다.

| `gradient_steps` | UTD | fps | 30초 내 성공 |
|---|---|---|---|
| **1** | **0.125** | **1,720** | O |
| 2 | 0.25 | 1,044 | O |
| 4 | 0.5 | 604 | O |

조용한 기계에서는 세 설정 모두 30초 안에 풀립니다. fps가 가장 높은 1을 씁니다.
CrossQ는 원 논문에서 UTD ≥ 1에서 이득을 보는 알고리즘이므로, 공정성을 위해
**UTD = 1 조건의 별도 비교**(`rl/runs_utd1`, `furuta_rl_utd.png`)도 같이 돌립니다.

### 처리량 측정 결과 (환경만, 학습 없이)

| 설정 | fps |
|---|---|
| dt 1 ms, DummyVecEnv(32) | 1,544 |
| dt 1 ms, SubprocVecEnv(6) | 3,422 |
| dt 2 ms, DummyVecEnv(32) | 2,944 |
| **dt 2 ms, SubprocVecEnv(24)** | **10,598** |

환경 스텝 자체도 227 → 128 µs로 줄였습니다: numpy 호출 제거, `mj_step(nstep=)`으로 파이썬
호출 5회 → 1회, 관측 버퍼 재사용. MuJoCo 스텝이 생각보다 비싼 이유는 `frictionloss`가
제약조건 2개를 만들어 솔버가 매 스텝 반복하기 때문입니다(정지 15 µs → 운동 중 32 µs).

이 최적화가 결론을 바꿉니다. 1,544 fps면 180초에 28만 스텝인데 PPO는 100만 스텝 넘게
필요했으므로, 최적화 없이는 PPO가 3분 안에 못 풀었습니다.

## 측정 환경 위생 (중요)

벽시계 시간을 재는 벤치마크는 **기계가 조용해야** 숫자가 의미를 갖습니다. 1차 실행은 이걸
놓쳐서 폐기했습니다(`rl/contaminated/`에 보존). 당시 상황:

- OP.GG 2개(203%), Blender(98%), ComfyUI(99%), Chrome(124%) 등이 6코어를 **616%** 점유
- 학습 프로세스가 CPU 상위 12위에도 안 들어갈 정도로 기아 상태
- 더 나쁜 건 **중간에 조건이 바뀐 것**: Blender와 ComfyUI가 실행 32분 뒤에 시작돼서,
  그 전에 측정된 PPO·A2C·SAC와 그 후에 측정된 TD3·DDPG가 서로 다른 조건이 됨
- 이 오염은 중립적이지 않습니다. PPO는 워커 24개, SAC는 프로세스 1개이므로 코어가 모자라면
  **PPO가 훨씬 심하게 손해**를 봅니다. 하필 비교하려던 축을 왜곡합니다.

그래서 `bench.py`가 런마다 오염 지표를 기록합니다.

- `calib_ms_before` / `calib_ms_after` — 학습 직전·직후에 고정된 계산(256×256 행렬곱 140회)을
  돌린 시간. 조용한 기계 **약 28 ms**, 중간 부하 48 ms, 1차 실행 당시 **108 ms**.
- `own_cpu_share` — 프로세스가 실제로 받은 CPU 코어 수. 기아 상태면 1 아래로 떨어지고,
  스레드를 과하게 주면 1을 크게 넘습니다(6스레드에서 5.13).

**재현할 때는 `calib_ms`가 28 ms 근처인지 먼저 확인하세요.** 벗어나면 다른 프로그램을 닫고
다시 시작해야 합니다.

그리고 **한 번으로는 부족합니다.** 지표를 기록해 두고도 읽지 않으면 소용이 없고, 오염은 특정
알고리즘에만 몰려 들어오기 때문에(1차에서는 TQC 4개 중 3개) 순위가 통째로 뒤집힙니다.
`rl/run_replicate.sh`가 전체를 다른 시각에 한 번 더 돌려 `runs_b` / `runs_utd1_b`에 넣고,
A·B·합본 그래프와 오염 표를 함께 만듭니다.

  A2C가 4/4인데 최종 0.82인 것은 닿았다가 일부 시드가 다시 무너졌다는 뜻입니다(1차에서는 0.32까지
  떨어졌습니다). TD3·DDPG의 0.71 / 0.79도 같은 현상입니다.
- **시드 편차**는 시간에 걸친 시드 간 성공률 최대−최소의 평균. 작을수록 "누가 돌려도 같은 결과".
- **최대 낙폭**은 리턴이 그때까지의 최고치에서 얼마나 떨어졌는지의 최댓값(괄호는 전체 상승폭 대비).

|---|---|---|---|---|---|---|
| SAC | 26 s | **21 s** | 1,461 | 1,795 | 38 ms | 29 ms |
| DDPG | 35 s | 66 s | 1,736 | 2,686 | **225 ms** | 28 ms |

**두 번 다 같았던 것** — 결론을 떠받치는 부분입니다.

- PPO의 낙폭 1% → 1%. 가장 매끄럽게 오른다는 것도 두 번 다.

**달라진 것**:

- **TQC가 6위 → 2위** (98초 → 49초). A에서 TQC 런 4개 중 3개가 오염돼 있었습니다(calib 216 ms).
  이것 때문에 아래 UTD 절의 결론 하나가 틀렸고, 고쳤습니다.

재현성 자체가 알고리즘을 가릅니다. SAC·PPO·CrossQ는 두 번의 숫자가 거의 같고,
TD3·DDPG·A2C는 반복마다 다른 이야기를 합니다.

**① 3분 미만**: 깨끗한 기계에서는 일곱 개 전부 통과합니다. 다만 A2C는 140초로 예산에 가장 가깝고,

최초 성공은 140초로 가장 느리고 리턴도 245에 그칩니다(SAC는 22초에 299).
**"빨리 많이 돌리는 것이 성능이 아니다"**를 한 장으로 보여 줍니다.

### 합성(composite) 알고리즘은 값어치가 있었나

`rl/figures/furuta_rl_utd.png`. 같은 알고리즘을 벽시계 최적(UTD 0.125)과 설계 조건(UTD 1)에서 각각.
아래는 **깨끗한 2차(B)** 기준입니다.

| | UTD 0.125 총 시간 | UTD 1 총 시간 | 낙폭 (UTD 0.125 → UTD 1) |
|---|---|---|---|
| SAC | **22 s** | 24 s | 7% → 1% |
| TQC | **49 s** | 77 s | 23% → **141%** |
| CrossQ | **54 s** | 85 s | 22% → **162%** |

세 알고리즘 **모두 UTD 0.125가 같거나 빠릅니다.** 그리고 TQC·CrossQ는 UTD를 올리면 **낙폭이
141~162%로 폭증**합니다(1차에서도 137% / 113%로 똑같이 나빴으므로 운이 아닙니다). 학습 도중
한 번 크게 무너졌다가 돌아온다는 뜻이라 교실에서 보여 주기 나쁩니다. SAC만 예외라서 두 설정
모두 매끄럽지만(20%/1%로 반복 간 편차가 커 단정하진 않습니다), **어느 설정에서도 합성
알고리즘이 SAC의 22초를 이기지 못했습니다.**

> **정정.** 1차만 보고 "UTD 0.125를 일괄 적용한 것이 TQC에 불리했다(100초 → 75초)"고 적었는데
> **틀렸습니다.** 그 100초는 UTD 설정이 아니라 배경 부하였습니다(TQC 런 4개 중 3개가 오염, calib 216 ms).
> 깨끗한 기계에서 TQC는 UTD 0.125에서 49초, UTD 1에서 74초 — **일괄 적용이 오히려 맞았습니다.**

### 고전 제어기 기준선

에너지 기반 스윙업 + LQR. LQR 이득은 튜닝이 아니라 모델에서 계산합니다(Bryson 규칙,
`K = [−0.370, 4.909, −0.174, 0.460]`, 설계 시간 0.06초).

| | 학습 시간 | 성공률 | 리턴 |
|---|---|---|---|
| 고전 제어기 | **0초** | 1.00 | 297.7 |
| SAC | 26초 | 1.00 | 297 |

**성능은 동급입니다.** RL이 더 잘해서 쓰는 것이 아니라, RL이 가르치려는 대상이기 때문에 씁니다.
고전 제어기는 그래프의 기준선으로 두어 "학습 곡선이 어디로 수렴하는가"를 보이게 합니다.

다만 설계에 들어간 사람 시간은 0이 아닙니다. 모델 유도, 에너지 법칙, 전환 조건 튜닝이 필요했고,
그 과정에서 두 가지를 틀렸습니다(아래 참고).

## 학습된 정책을 들고 시작하기 (warm start)

`rl/warmstart.py`, 그림은 `furuta_rl_warmstart.png` / `..._ppo.png` / `..._warm_compare.png`.
출발점은 같은 과제에서 180초 학습해 둔 정책입니다. 예산 50초, 시드 3개.

**"정책을 들고 간다"는 말은 모호합니다.** off-policy에서는 무엇을 들고 가느냐로 결과가 갈립니다.

| SAC | t=0 성공률 | 최초 성공 | 학습 중 최저 리턴 | 최종 |
|---|---|---|---|---|
| 맨 처음부터 | 0.00 | 17 s | −486 | 1.00 / 299 |
| **배우만** | 1.00 | 0 s | **−313** | 1.00 / 296 |
| **배우+비평가** | 1.00 | 0 s | **298** | 1.00 / 301 |
| 배우+비평가+버퍼 | 1.00 | 1 s | 298 | 1.00 / 299 |

배우(정책)만 복사하면 **난수 비평가가 멀쩡한 정책을 2초 만에 끌어내립니다**(300 → −170).
원래 수준으로 돌아오는 데 30초가 걸려, 구간에 따라서는 맨 처음부터 하느니만 못합니다.
비평가까지 들고 가면 리턴이 **시작값 아래로 한 번도 내려가지 않습니다**(최저 298 = 시작값).
재생버퍼를 미리 채우는 것은 0.6초만 손해 보고 이득이 없었습니다.

| PPO | t=0 성공률 | 최초 성공 | 학습 중 최저 리턴 | 최종 |
|---|---|---|---|---|
| 맨 처음부터 | 0.00 | 3시드 중 2개 | −489 | 0.67 / 242 |
| **배우만** | 1.00 | 0 s | **300** | 1.00 / 302 |
| 배우+값함수 | 1.00 | 0 s | 301 | 1.00 / 301 |

**PPO는 배우만 들고 가도 무너지지 않습니다.** 값함수가 쓰이는 방식이 다르기 때문입니다.

- SAC의 비평가 `Q(s,a)`는 "이 행동의 가치는 얼마"를 **직접** 가르칩니다. 난수면 틀린 방향을
  가르치고, 정책은 그 방향으로 끌려갑니다.
- PPO의 값함수 `V(s)`는 실제로 받은 보상에서 빼는 **기준선**입니다. 난수여도 이점 추정이
  시끄러워질 뿐 부호가 뒤집히지 않고, clip이 한 번에 크게 바뀌는 것을 막습니다.

### 규칙이 바뀌면

교육용 키트에서 실제로 일어나는 일입니다. 학생이 규칙을 바꾸면 들고 온 비평가는 **다른 보상**에
대해 학습된 값이라 틀린 값을 가르칠 수 있습니다.

| 규칙 변화 | | 맨 처음부터 | 들고 시작 |
|---|---|---|---|
| 작음 (힘 아끼기 약→강) | SAC | 19 s | **0 s** |
| 큼 (부드럽게 약→강) | SAC | **3시드 중 1개만 성공** | **0 s, 3/3** |
| 큼 (부드럽게 약→강) | PPO | **0/3 성공** | **0 s, 3/3** |

규칙을 세게 바꾸면 **맨 처음부터는 50초 안에 못 배웁니다**(PPO는 세 시드 모두 실패).
들고 시작하면 전부 0초에 됩니다. 즉 이 경우 warm start는 "빨라진다"가 아니라
**"되느냐 안 되느냐"의 문제**입니다.

다만 **왜 되는지**는 정확히 말해 둘 필요가 있습니다. 들고 온 정책이 새 규칙에서도 이미 잘하기
때문입니다(t=0에 리턴 275~281). 규칙이 바뀌어도 "진자를 세운다"는 최적 행동 자체는 크게
달라지지 않습니다. 최적 행동이 통째로 달라지는 과제에서는 이 결과가 그대로 가지 않습니다.

### 그래서 앱에는

앱의 기본 규칙 아홉 조합은 미리 학습해 두고, 블록으로 만든 새 규칙은 **가장 가까운 정책에서
출발해** 화면 안에서 CEM으로 다듬습니다(`app/src/js/learn.js`). 여기서 잰 것과 같은 전략이고,
CEM은 비평가가 없어 위의 함정 자체가 없습니다.

## 동역학 기반 제어기를 PPO에 붙이기

`rl/prior_rl.py`, 그림은 `furuta_rl_prior.png`. 출발 제어기는 `rl/classical.py` 가 모델에서
계산한 에너지 스윙업 + LQR(설계 0.06초, 튜닝 없음)입니다. 보상·환경·PPO 설정은 벤치마크와
완전히 같고 **제어기를 어떻게 끼우느냐만** 다릅니다. 예산 60초, 시드 3개.

| 방식 | t=0 리턴 | 최초 성공 | 그중 사전학습 | 최종 |
|---|---|---|---|---|
| **잔차 학습** (Silver / Johannink) | 298 | **0 s** | — | 1.00 / 297 |
| **제어 정규화 λ=3** (CORE-RL) | 32 | **5 s** | — | 1.00 / 299 |
| 제어 정규화 λ=9 | 10 | 6 s | — | 1.00 / 301 |
| BC 사전학습 | 79 | 13 s | **10.6 s** | 1.00 / 302 |
| DAPG | 79 | 14 s | 10.7 s | 1.00 / 301 |
| PPO 그대로 | −489 | 45 s | — | 1.00 / 296 |
| Jump-Start (고정 일정) | −489 | **0/3 미달성** | — | 0.00 / 46 |

- **잔차 학습**은 `u = clip(u_prior + 0.5 a)`. 0초에 성공하지만 그 성적은 **제어기의 것**이지
  PPO의 것이 아닙니다. 60초를 더 돌려도 297로, 제어기 자체(297.7)를 넘지 못했습니다.
  잔차 폭을 0.5로 제한했기 때문이고, 이 과제에서는 제어기가 이미 보상에 거의 최적이라
  넘을 여지가 작습니다.
- **제어 정규화**가 이 중 가장 값어치가 있었습니다. `u = (λ u_prior + a)/(1+λ)` 로 섞기만
  했는데 45초 → 5초로 **9배**, 그러면서 최종 리턴은 제어기보다 **위**(299~301)입니다.
  제어기가 초반을 끌어주되 정책이 벗어날 여지를 남기기 때문입니다.
- **BC 사전학습**은 RL 구간 자체는 3초밖에 안 걸리지만 **BC에 10.6초**가 듭니다. 그림의 연한
  칸이 그 부분입니다. 합쳐서 13초로 PPO 그대로보다 3.5배 빠릅니다.
- **DAPG의 증강 항은 이 과제에서 이득이 없었습니다**(13초 vs 14초, 최종 302 vs 301).
  BC 사전학습이 이미 할 일을 다 했다는 뜻입니다.

### BC가 이 제어기를 잘 못 따라합니다

시연 6만 개 × 500 에폭을 줘도 성공률 0.20이 최고였습니다(격자 탐색). 스윙업 법칙이
`sign(·)` 이 들어간 **bang-bang** 이라, 64×64 신경망을 MSE로 맞추면 전환면 근처에서 평균이
0 쪽으로 뭉개집니다 — 바로 거기서 최대 토크를 넣어야 하는데도. 그래서 BC 출발점은 리턴 79에
그치고, 나머지는 PPO가 메웁니다. 설정은 6만 개 × 60 에폭(10.6초)으로 두었습니다.

### Jump-Start 실패는 방법이 아니라 제 구현 탓입니다

원 논문은 가이드 구간 `h` 를 **성능에 따라** 줄입니다. 여기서는 예산의 50%에 걸쳐 선형으로
줄이는 고정 일정으로 단순화했고, 그 결과 `h` 가 0이 되는 시점에 정책은 **매달린 상태에서의
스윙업을 한 번도 연습한 적이 없는** 상태였습니다. 3시드 모두 미달성.
이것은 "JSRL이 이 과제에 안 맞는다"가 아니라 **고정 일정 커리큘럼이 60초 예산에 안 맞는다**는
결과로 읽어야 합니다.

구현 메모: 가이드는 `PriorEnv.reset()` **안에서** 돌립니다. 밖에서 끌면 정책이 고른 행동과
실제 실행된 행동이 달라져 학습 신호가 오염됩니다.

## SAC를 벽시계 기준으로 조율하기

`rl/sac_speed.py`, 그림은 `furuta_rl_sac_speed.png` (`python rl/plot_speed.py`).
출발점은 벤치마크의 SAC 그대로입니다(환경 8개, 배치 256, 64×64, 학습률 3e-4). 평가 간격만
5초에서 1초로 줄였습니다. 벤치마크의 "18초"는 5초 눈금이라 시드별로 15초 아니면 20초였고,
1초 눈금으로 다시 재면 기본 설정은 **16.0초**(16 / 17 / 15)입니다.
"풀린 시각"은 성공률 0.8 이상을 3번 연속 유지하기 시작한 학습 시간입니다.

### 시간이 어디에 쓰이나

| 구간 | 시간 | 비중 |
|---|---|---|
| 환경 스텝 (8개) | 0.88 ms | 21% |
| 행동 선택 | 0.20 ms | 5% |
| **업데이트 1회 (배치 256)** | **3.15 ms** | **75%** |

업데이트 시간은 배치 256에서 3.0 ms, 1024에서 4.9 ms, 4096에서 12.8 ms입니다. 약 2.4 ms가
배치 크기와 무관한 PyTorch 호출 오버헤드입니다.

### 설정을 하나씩 바꿨을 때 (시드 3개)

| 설정 | 풀린 시각 | 기본 대비 | 그때 업데이트 횟수 |
|---|---|---|---|
| **학습률 1e-3** | **10.0 s** | **−38%** | 2,162 |
| 학습률 3e-3 | 11.4 s | −29% | 2,370 |
| 환경 4개 | 14.7 s | −8% (시드 범위 겹침) | 3,448 |
| 학습 시작 500스텝 | 15.7 s | −2% | — |
| **기본** | **16.0 s** | — | 3,375 |
| 비평가 LayerNorm | 16.1 s | 0% | 2,420 |
| 엔트로피 계수 0.1에서 시작 | 16.7 s | +4% | — |
| 스텝당 업데이트 2회 | 16.7 s | +4% | 3,950 |
| 배치 512 / 1024 | 17.0 / 17.1 s | +6% | — / 2,572 |
| 환경 16개 | 18.1 s | +13% | 3,118 |
| 배치 2048 | 22.8 s | +42% | 2,435 |
| 타깃 갱신 τ 0.02 | 25.7 s | +60% | 5,451 |
| 환경 32개 | 25.8 s | +61% | 3,271 |
| 비평가 256×256 | 26.5 s | +65% | 2,784 |
| 3-step 리턴 | 45.1 s | +181% | 9,023 |

**필요한 것은 데이터가 아니라 업데이트 횟수입니다.** 환경을 4개에서 32개로 늘리면 풀릴 때까지
모은 전이가 1.6만 → 10.7만 개로 7배가 되는데, 필요한 업데이트는 3,100~3,450번으로 같습니다.
그래서 환경을 늘리면 업데이트가 느려지는 만큼 그대로 손해입니다. 배치를 키우거나 LayerNorm을
넣으면 필요한 업데이트는 약 2,500번으로 줄지만 업데이트 하나가 그만큼 비싸져 상쇄됩니다.

병렬 환경과 큰 배치로 속도를 내는 FastTD3 계열의 처방은 GPU에서 환경 수천 개를 돌리는 상황의
것이고, CPU에서 환경 스텝이 싸고 신경망이 작은 이 과제에서는 반대 방향이었습니다.

### 학습률 주변 (시드 3개)

| 학습률 | 3e-4 | 6e-4 | 1e-3 | 1.5e-3 | 2e-3 | 3e-3 |
|---|---|---|---|---|---|---|
| 풀린 시각 | 16.0 s | 11.7 s | 10.0 s | 10.7 s | 10.4 s | 11.4 s |

1e-3에서 2e-3까지 평평합니다. 학습률 1e-3 위에 환경 4개(9.7초), 배치 512(11.4초),
LayerNorm(11.7초), 학습 시작 500스텝(10.4초)을 겹쳐도 10초 아래로 확실히 내려가지 않았습니다.
환경을 2개, 1개로 줄이면 11.4초, 12.7초로 다시 느려집니다 — 이번에는 데이터가 모자라
필요한 업데이트가 2,683번, 3,266번으로 늘어납니다.

### 끝까지 돌렸을 때 (180초, 시드 4개, 평가 2초 간격)

스크리닝은 풀리면 일찍 멈추므로, 높은 학습률이 끝까지 안정적인지 따로 확인했습니다.

| 설정 | 풀린 시각 | 시드별 | 최종 성공률 | 최종 리턴 | 낙폭 | 풀린 뒤 1.00 아래로 내려간 평가 |
|---|---|---|---|---|---|---|
| 기본 (3e-4) | 16.0 s | 16 / 16 / 16 / 16 | 1.00 | 299 | 16% | 없음 |
| **학습률 1e-3** | 11.0 s | 12 / 10 / 10 / 12 | 1.00 | 304 | 14% | 1회 (시드 2, 24초, 0.8) |
| 학습률 2e-3 | 10.0 s | 10 / 10 / 10 / 10 | 1.00 | 305 | 13% | 없음 |

학습률을 올려도 끝까지 무너지지 않고, 최종 리턴은 오히려 조금 높습니다. 12개 런 모두
`calib_ms` 27~31로 깨끗했습니다. 낙폭 수치는 평가 간격이 달라(2초) 위 벤치마크 표의 7%와
직접 비교할 수 없고, 이 표 안에서만 비교해야 합니다.

### 정리

- 바꿀 것은 학습률 하나입니다: `learning_rate=1e-3`. 16.0초 → 10~11초.
- 설정만으로는 약 10초가 바닥입니다. 10초 = 업데이트 약 2,200번 × 한 번에 4.65 ms이고,
  그 아래로 가려면 업데이트 한 번의 비용(그중 2.4 ms가 호출 오버헤드)을 줄여야 합니다.
- `bench.py`의 SAC 설정은 바꾸지 않았습니다. 위 벤치마크 표와의 비교 가능성을 유지하기 위해서입니다.

## 강건성 (`rl/robust.json`)

학습된 정책을 세 가지로 시험했습니다. 숫자는 "마지막 2초를 도립으로 유지"한 비율입니다.

| | 상태 복원 | 이상적 | 12비트 | +차분속도 | **+20 ms 지연** |
|---|---|---|---|---|---|
| SAC·TD3·TQC | 100% | 100% | 100% | 100% | **0%** |
| PPO | 98~100% | 100% | 100% | 100% | 0~53% |
| CrossQ | 100% | 100% | 100% | 100% | **100%** |
| 고전 LQR+에너지 | **63%** | 100% | 100% | **0%** | 0% |

- **상태 복원**: 진자 각도 전 범위 × 각속도 ±6 rad/s, 125개 초기조건에서 다시 세우기.
  RL 정책이 98~100%, 고전 제어기는 63%. **넓은 상태에서는 RL이 더 강합니다.**
- **충격 외란**: 에피소드 중간에 진자를 ±12 rad/s로 쳐도 RL은 100% 복원, 고전은 10 rad/s부터 실패.
- **차분 속도**(AS5600 각도를 차분해 속도를 얻는 실제 구현): RL 100%, **고전 0%**.
  미분 이득이 양자화 잡음을 증폭합니다.
- **20 ms 지연**: 대부분 0%. 이것이 실기 이식의 최대 위험입니다.

### 지연 문제와 해법 (측정)

20 ms는 물리적으로 불가능한 조건이 아닙니다. 같은 지연에서 LQR은 100% 유지합니다. 문제는
**지연을 모르고 학습한 정책**입니다. 세 가지를 재봤습니다.

| 학습 방식 | 0 ms | **20 ms** | 40 ms | 20 ms + 0.5° 잡음 |
|---|---|---|---|---|
| A 지금 방식(지연 0으로 학습) | 100% | **0%** | 0% | 0% |
| B 지연 랜덤화만 | 100% | **0%** | 0% | 0% |
| C 랜덤화 + **행동 기억** | 100% | **100%** | 0% | **100%** |

**지연 랜덤화만으로는 부족하고, 정책이 자기가 방금 낸 명령을 볼 수 있어야 합니다.** 지연이 있으면
각도·속도만으로는 상태가 불완전하기 때문입니다(날아가고 있는 토크를 모름). 관측 끝에 최근 명령
두 개를 붙여 6 → 8개로 만들면 해결됩니다. 앱에 넣는 정책은 이 방식으로 학습합니다(`train_rules.py`).

**40 ms에서는 LQR을 포함해 아무것도 버티지 못합니다.** 펌웨어 요구사항입니다 — 센서 읽기부터
토크 명령까지 **한 제어 주기(50 Hz에서 20 ms) 안에** 끝나야 합니다.

## 작업하며 틀렸던 것

재현할 때 같은 함정을 피하도록 적어 둡니다.

1. **배경 부하.** 1차 실행은 다른 프로그램이 6코어를 616% 점유한 상태에서 측정돼 폐기했습니다
   (`rl/contaminated/`). 더 나쁜 건 실행 도중 조건이 바뀐 것이고, 워커 24개를 쓰는 PPO가 프로세스
   1개인 SAC보다 훨씬 심하게 손해를 봤습니다. 지금은 런마다 `calib_ms`를 기록합니다.
2. **지연 off-by-one.** `action_delay_steps=1`이 실제로는 2스텝 지연이었습니다(큐를 `delay+1`개로
   초기화). 이것 때문에 "20 ms에서 전부 실패"라는 틀린 결론을 낼 뻔했습니다. 실제 20 ms는 대부분
   괜찮고 40 ms가 절벽입니다.
3. **armature 이중 계산.** MuJoCo의 질량행렬에는 `dof_armature`가 이미 들어 있는데 JS 모델에서 또
   더했습니다. 궤적이 1144° 어긋나고 나서야 찾았습니다.
4. **마찰이 선형화를 망가뜨림.** 쿨롱 마찰의 `tanh` 근사는 0 근처 기울기가 `0.012/0.005 = 2.4`라
   가짜 점성감쇠가 되어 LQR 극점을 −461까지 끌고 갔고, 이득이 898까지 나왔습니다. 선형화는
   마찰 없는 플랜트로 해야 합니다.
5. **오염된 1회 측정으로 결론을 냈다.** "UTD 일괄 적용이 TQC에 불리했다"고 적었지만, 독립 반복을
   돌려 보니 그 숫자(TQC 100초)는 UTD가 아니라 배경 부하였습니다. 깨끗한 기계에서는 49초이고
   일괄 적용이 맞았습니다. **`calib_ms`를 기록해 두고도 그 값을 보지 않고 결론을 쓴 것**이 실수입니다.
   오염 지표를 남기는 것만으로는 부족하고, 결론을 쓰기 전에 읽어야 합니다.
6. **벽시계 숫자를 한 번만 재고 순위를 매긴 것.** 한 번의 측정으로 매긴 순위는 중간 순위가
   통째로 뒤바뀔 수 있습니다(TQC 6위 → 2위). 지금은 A/B 두 번을 돌려 **두 번 다 같은 것만**
   결론으로 씁니다. 재현 스크립트는 `rl/run_replicate.sh`.
