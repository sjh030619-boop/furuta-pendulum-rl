# 키트 쪽 프로그램 (라즈베리파이)

앱(노트북)과 키트(Pi)를 USB 로 잇는 부분입니다. 규약은 `../PROTOCOL.md`(v2).

**한 줄 요약**: 앱이 고친 정책을 Pi 로 올리고, Pi 가 그 정책을 50 Hz 로 직접 돌리고, 그동안의 상태를 앱에 보내 줍니다.

| 파일 | 내용 |
|---|---|
| `kit_server.py` | 대기 프로그램. Pi 에서 계속 떠 있다가 앱의 명령을 받음 |
| `kit_cal.py` | 키트 맞추기 계산 (영점 식, 팔 관성·마찰, 진자 주기). 기록만 받아 계산하고 모터는 안 씀 |
| `kit_fake.py` | 가짜 키트. 모터·센서를 계산으로 흉내 (`--fake`). can0, I2C 를 쓰지 않음. 받침 기울기도 흉내 냄 |
| `test_replay.py` | 실기 기록을 다시 넣어 토크 경로·회전 감지가 실기와 같은지 확인 |
| `test_fake.py` | 가짜 키트로 규약 전체를 끝까지 시험 (TCP) |
| `test_serial_pty.py` | 직렬 포트 경로와 제어 주기 시험 (Pi·리눅스) |
| `kit_client.py` | 앱 없이 명령줄로 점검·올리기·실행 (실기 첫 확인용) |
| `kit-server.service` | 부팅 때 자동으로 띄우는 systemd 예시 (아직 설치하지 않음) |

## 모터 구동부는 조원 코드 그대로

`kit_server.py` 는 `pi_host/run_policy.py`, `session.py`, `canguard.py` 를 **불러서** 씁니다(고치지 않음).
`Motor`, `Pendulum`, `speed_torque_limit`, `brake_limit`, `torque_to_iq`, `graceful_stop`, `session.preflight` 가 그대로입니다.
새로 쓴 것은 줄을 주고받는 부분, 정책을 받는 부분, 제어 루프의 이음매 40줄, 그리고 멈춤 조건 둘(진자 계속 회전, 앱 신호 끊김)입니다.

토크 경로는 실기에서 검증한 명령과 같습니다: `run_policy.py --run --tau 2.52 --iq-max 120` (제동 제한 5 W / 20°, 마찰 보상 없음).

## 키트 맞추기 (2.1.0, 2026-11-25)

받침 수평은 놓을 때마다 바뀔 수 있고, 팔·진자의 물성은 키트마다 정해져 있다는 생각으로 둘로 나눴습니다.

| | 언제 | 하는 일 | 걸리는 시간 |
|---|---|---|---|
| **수평 측정** | **실행할 때마다** (`R`) | 진자가 멈춘 뒤 팔을 120°씩 두 번 돌려 세 자리에서 진자 영점 RAW 를 잼 → 받침 기울기·방향 → 이번 실행의 영점 식 `C + A·cos(θ − φ)` 으로 정책에 들어가는 진자 각도를 고침 | 가짜 키트 6초. 실기는 자리마다 4.4초쯤 걸렸던 기록으로 보아 약 12초 (아직 실기에서 안 잼) |
| **키트 맞추기** | **연결할 때, 앱에서 확인 단추를 누른 뒤에만** (`G`) | ① 영점 네 자리(90°씩) → 진자 자석 영점 C ② 마찰 펄스 6번(조원 `measure_friction` 그대로) → 팔 관성 J, 쿨롱 Fc±, 점성 b ③ 브레이크로 팔을 잠그고 진자 자유진동 10초 → 작은 진폭 주기 | 가짜 키트 30초, 실기 약 40초 예상 |

- 수평 측정의 진자 영점 C 는 키트 맞추기 값(`<log-dir>/kit_cal_latest.json`)을 쓰고, 없으면 `session.py` 의 `ZERO_C` 를 씁니다.
- 수평 측정에서 멈추는 경우: 받침이 5° 넘게 기울었음(`R END tilt`), 세 자리 값이 영점 식에 4카운트(0.35°) 넘게 안 맞음(`R END level`, 진자 자석이 밀렸거나 키트 맞추기 값이 다른 키트 것).
  두 경우 모두 팔만 수평 측정에 돌리고 정책은 돌리지 않습니다.
- 수평 측정·키트 맞추기 중에도 정지(`X`)·앱 신호 끊김·팔 600 dps·모터 응답 없음이면 멈추고 `graceful_stop` 합니다.
  단, 마찰 펄스(약 7초)는 조원 함수를 그대로 부르므로 그동안은 정지 명령을 펄스가 끝난 뒤에 처리합니다(펄스마다 0.8초, 1 A 이하, 자체 속도 한계 있음).
- 키트 맞추기 기록: `<log-dir>/kit_cal_<시각>.json`, `_arm.csv`(마찰 펄스, `kit_id_*.csv` 와 같은 열), `_swing.csv`(진자 자유진동).
  조원의 `kit_params_latest.json` 은 건드리지 않습니다.
- **아직 앱 시뮬레이션에 넣지 않았습니다.** 지금은 재서 보여 주고(정책이 배운 폭과 비교), 진자 영점에만 씁니다.

### 받침 기울기가 정책에 주는 영향 (시뮬레이션)

MuJoCo 의 중력 방향을 기울여 가운데 칸 정책(`sac_s1e1`)을 돌렸습니다. 조건 8 × 시작 16 × 기울기 방향 4 = 512회, 판정은 `s2r/evaluate.py` 의 엄격 기준.
'보정'은 매 실행 수평 측정이 맞았을 때(정책이 진짜 수직 기준 각도를 봄), '보정 없음'은 받침이 평평하다고 가정한 영점을 쓸 때입니다. `s2r/tilt_eval.py`, `s2r/tilt_eval2.py`.

| 기울기 | 보정 없음 | 보정 | 세운 뒤 팔이 흐르는 빠르기 (없음 / 보정) |
|---|---|---|---|
| 0.01° (평평, 기준) | — | — | 74 / 74 °/s |
| 1° | 96% | 96% | |
| 2° | 99% | 95% | 3 / 67 °/s |
| 3° | 99% | 95% | |
| 5° | 99% | 95% | 1 / 64 °/s |
| 10° | 86% | 67% | |

- 받침이 기울면 진자가 매달리는 방향이 팔 각도에 따라 ±기울기만큼 바뀝니다(2.4° 기울기 → ±2.40°, 영점 식의 진폭과 같음). 보정은 바로 이 양을 빼는 것이고,
  남는 물리 차이(중력이 cos 기울기만큼 약해짐 0.1% 미만, 팔에 걸리는 작은 중력 토크)는 2차 효과입니다. 그래서 몇 도까지는 **다시 학습할 필요가 없습니다.**
- 뜻밖에 이 정책은 **보정하지 않아도** 5°까지 잘 세웠습니다. 평평한 곳에서 이 정책은 세운 뒤 팔을 천천히 계속 돌리는데(평균 74°/s),
  보정하지 않은 기울기가 '팔 각도에 따라 바뀌는 영점'이 되어 팔을 한 자리에 붙잡는 용수철처럼 작용했습니다(팔 흐름 1~3°/s, 평균 힘도 절반).
  보정하면 평평할 때처럼 팔이 계속 돌고, 그 상태에서 팔 쪽 중력 토크가 더해져 통과율이 조금(3~4%p) 떨어집니다.
- 그래도 대기 프로그램은 **보정하는 쪽**으로 두었습니다: 놓는 자리에 따라 결과가 달라지지 않게(수업에서 같은 정책이 같은 행동), 그리고 정책이 배운 가정(진짜 수직 기준)과 맞추려고.
  팔이 계속 도는 것은 받침이 아니라 정책 쪽 문제라서, 보상에 팔 자리를 넣는 식으로 따로 다루는 것이 맞습니다.
- 10° 에서는 둘 다 떨어지므로, 받침이 5° 넘으면 실행하지 않고(`R END tilt`) 수평을 맞추라고 안내합니다.

### 계산이 맞는지 (모터 없이 확인)

| 확인 | 결과 |
|---|---|
| 팔 관성·마찰 맞춤 `kit_cal.fit_arm` 을 조원의 실기 측정 기록 6개(`kit_id_*.csv`)에 | 조원의 MuJoCo 재생 맞춤과 J 차이 0.0002~0.0004 (= 진자 몸체 관성 0.00024, 이쪽은 몸체 포함), Fc±·b 는 소수 셋째 자리까지 같음 |
| 진자 주기 `kit_cal.fit_swing` 을 실기 자유진동 기록 2개(11-18)에 | 0.700 s, 0.700 s (주기마다 표준편차 1.6 ms) |
| 같은 계산을 모델 물리(가짜 키트)에 | 0.726~0.729 s, 모델 예측 0.724 s 와 0.3~0.7% |
| 가짜 키트: 받침 2.0°/100°, 영점 +5 | 키트 맞추기 1.9°/105°, C +3.5~+4.8 · 실행마다 측정 1.9~2.2° · 관성·마찰 참값과 1% 안 |

**새로 보인 차이**: 실기 진자의 작은 진폭 주기(0.700 s)가 앱·학습 모델(0.724 s)보다 3.4% 짧습니다.
모델의 진자 관성에 자유진동 맞춤(M2)에서 얻은 armature 2.1×10⁻⁵ 이 더해져 있어서입니다(빼면 0.702 s).
M2 는 큰 진폭(133°) 기록까지 함께 맞춘 값이라 작은 진폭 주기와는 어긋난 것으로 보입니다. 정책 학습 조건에는 진자 쪽 무작위화가 없습니다.
이 차이가 실기에서 세우는 시간이 시뮬레이션보다 늦은 것(2.9·4.5초 대 2.3초)과 관계있는지는 아직 모릅니다.

## 돌려 보기

### 1. 이 PC 에서 가짜 키트로 (Pi 없이)

PowerShell 창 하나에서 가짜 키트를 띄웁니다(프로젝트 루트에서):

```powershell
.venv\Scripts\python.exe app\kit\kit_server.py --fake --tcp 127.0.0.1:47800 --host-dir s2r\pi_mirror_20261124\pi_host
```

다른 창에서 앱을 엽니다(`app` 폴더에서):

```powershell
$env:PS_KIT_TCP = "127.0.0.1:47800"; npm start
```

앱의 `키트 연결하기` 목록에 `tcp://127.0.0.1:47800 (개발용 TCP 연결)` 이 나옵니다. `PS_KIT_TCP` 가 없으면 이 항목은 나오지 않습니다.

### 2. Pi 에서 시험만 (모터 미사용)

Pi 의 `~/rev11_s2r/kit/` 에 복사해 두었습니다(조원 폴더 `pi_host/` 는 건드리지 않음).

```bash
cd ~/rev11_s2r
python3 kit/test_replay.py pi_host pi_host/logs/stage5_20261124=pi_host/policies_s2r/stage5 pi_host/logs/stage2_20261124=pi_host/policies_s2r
python3 kit/test_fake.py pi_host kit/test_policy.npz
python3 kit/test_serial_pty.py pi_host kit/test_policy.npz
```

### 3. 실기에서 처음 돌릴 때 (사람이 키트 옆에)

USB 배선 전에도 SSH 로 먼저 확인할 수 있습니다. Pi 에서:

```bash
cd ~/rev11_s2r && python3 kit/kit_server.py --tcp 127.0.0.1:47800
```

노트북에서 그 포트를 끌어옵니다:

```powershell
ssh -N -L 47800:127.0.0.1:47800 furuta-pi
```

그리고 위 1번처럼 `PS_KIT_TCP` 로 앱을 열어 연결합니다. 순서:

1. `키트 상태` 탭의 **키트 점검** — 모터를 움직이지 않습니다(0x9A·0x92·0x9C 와 AS5600 읽기만). can0·모터 응답·진자 영점이 나옵니다.
2. 따라 하기의 가운데 칸(약하게·약하게) 정책으로 **실제 키트 → 시작하기**. 2026-11-24 실기에서 3/3 세운 바탕 정책과 같은 보상·같은 환경으로 학습했지만
   다른 신경망이라, 이 정책 자체는 실기에서 처음입니다(시뮬 안전 시험 40칸 중 파이썬 39 · 앱 37, 128칸 중 127칸).
3. `kit_server.py` 를 띄운 창에 `종료: iq 0 ... -> 0x81 -> 0x78 -> 0x80` 이 찍히는지 봅니다.
4. 기록은 `pi_host/logs/kit_server_<시각>.csv`(run_policy 와 같은 열) + `.txt`(끝난 까닭) + `_policy.npz`(올라온 정책, `run_policy.py --policy` 로 다시 돌릴 수 있음).

대기 프로그램은 대기 중에 can0 을 열지 않으므로, 조원이 `run_policy.py` 를 따로 돌려도 부딪히지 않습니다.
다만 대기 프로그램이 실행(`R`) 중일 때 다른 스크립트를 시작하면 그쪽 점검(1초 듣기)에서 걸립니다.
`canguard.py` 의 `FOREIGN_PATTERNS` 에 `kit_server.py` 를 넣어 두면 더 일찍 걸립니다(조원 파일이라 넣지 않았습니다).

## USB 로 잇는 방법

앱은 COM 포트만 있으면 됩니다. Pi 쪽에서 그 COM 포트의 반대편을 무엇으로 만들지가 고를 것입니다.
Pi 의 지금 설정(2026-11-25 읽어 봄): `dtparam=uart0=on` 켜져 있음, `/dev/ttyAMA0` 있음, 콘솔은 `serial0`(= `ttyAMA10`, 디버그 단자) 쪽, USB 장치 모드는 설정돼 있지 않음.

| 방법 | Pi 쪽 포트 | 필요한 것 | 지금 바로 되나 |
|---|---|---|---|
| **B1. USB-시리얼 어댑터 2개를 맞물림** (또는 USB 널모뎀 케이블) | `/dev/ttyUSB0` | 어댑터 2개: TX↔RX, RX↔TX, GND↔GND. 하나는 Pi 의 USB-A, 하나는 노트북 | 예. Pi 설정을 바꾸지 않음 |
| **B2. USB-시리얼 어댑터 1개 → Pi GPIO 14/15** | `/dev/ttyAMA0` | 3.3 V 어댑터 1개, 점퍼선 3가닥 | CAN 보드가 GPIO 14/15 를 쓰지 않는지 확인 필요 |
| **A. USB-C 케이블 하나** (Pi 를 USB 장치로) | `/dev/ttyGS0` (확인 필요) | Pi 전원을 GPIO 핀으로 따로 공급, `config.txt` 수정, 재부팅 | 아니오. 아래 참고 |

- **시제품은 B1 또는 B2**, 완성품은 **A** 를 권합니다. 어느 쪽이든 `kit_server.py --serial <포트>` 만 다릅니다.
- 어댑터 칩이 CP2102·FT232 면 Windows 가 드라이버를 알아서 잡는 편이고, CH340 은 드라이버를 깔아야 할 수 있습니다.
- **A 를 하려면**: 라즈베리파이 공식 자료에 따르면 Pi 5 는 USB-A 단자(PCIe 쪽 컨트롤러)로는 장치 모드가 안 되고,
  전원 단자인 USB-C 로만 됩니다. 그래서 USB-C 를 데이터에 쓰는 동안 전원은 GPIO 헤더로 넣어야 합니다.
  설정은 `/boot/firmware/config.txt` 에 `dtoverlay=dwc2,dr_mode=peripheral` 을 넣고 `g_serial` 모듈을 올리는 것입니다.
  Pi 5 에서 `/dev/ttyGS0` 가 실제로 생기는지는 **확인하지 못했습니다**. 부팅 설정을 바꾸고 재부팅해야 하므로 조원과 상의한 뒤에 하세요.

### 부팅 때 자동으로 띄우기

`kit-server.service` 가 예시입니다. 포트 이름을 정한 뒤 `/etc/systemd/system/` 에 넣고 `systemctl enable --now kit-server` 하면 됩니다.
아직 설치하지 않았습니다(포트가 정해지지 않았고, Pi 의 시스템 설정을 바꾸는 일이라서).
